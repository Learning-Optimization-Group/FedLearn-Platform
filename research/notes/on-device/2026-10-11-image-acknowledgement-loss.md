# Accepted image upload with lost completion

A fresh original-pneumonia run exercises the actual mounted vivo training
provider and canonical Linux CPU client: three FedAvg rounds, 16 balanced local
images per client, native `73ca4bf` and unchanged JavaScript/Linux `50a01ca`.
The installed Debug APK, numerical core and replay binary match their qualified
hashes. No application or training behavior changes in this follow-up.

While the Linux peer is held, the phone completes its first model upload. The
real coordinator records that contribution. A new owned proxy observes the
successful upstream gRPC completion before forwarding the current response
block, withholds that block and cuts connections for eight seconds. The phone
reports `SubmitModelUpdateStream failed` and has no durable submitted checkpoint,
even though the server has already accepted its update.

The provider re-registers on the same run and submits round one again. Both
complete attempts receive successful upstream responses, but the authoritative
accepted-update recorder contains one phone contribution. The phone saves
checkpoint one before the Linux peer is released. A `received` response alone
is not evidence of an additional accepted update. Matching full-update hashes
are client declarations; duplicate retry tensor equivalence is not independently
captured. Exact replay verifies the first accepted output whose client completion
was lost.

Three rounds finish with six unique 16-example contributions, checkpoint three
and no foreground training service. All three original accepted phone outputs
and all three Linux outputs replay bit-for-bit. Changing one label changes each
client's result. Their aggregate matches the registered final checkpoint.
This model has no integer counters or BatchNorm variance tensors, so generic
checks on those states add no coverage. All 14 transferred replay files match
their hashes, both replay jobs exit successfully, owned helpers are absent and
all 33 saved dataset files remain unchanged. The
[receipt](../../results/on-device/android-image-acknowledgement-loss-2026-10-11.json)
binds the source, runtime, outputs and private evidence.

The new real-gRPC transport smoke fails against the previous partial-upload
proxy because that cut precedes acceptance. After the response-side gate is
added, the synthetic server accepts the full payload, the client sees
`UNAVAILABLE`, and duplicate retry counts once with unchanged full payload hashes.
That smoke uses a fixture's deduplication and is separate from the live platform
coordinator. Ten unchanged observer checks pass on each host. Request bytes are
forwarded before observation; response bytes are observed before forwarding.
All normal forwarding is byte-identical, and the selected response block is
intentionally withheld. The observer logs no credentials or model contents.
Earlier hash-bound drivers and receipts remain unchanged. Collection initially
read the replay log before it was created; both replay jobs continued. A
missing-log regression fails before the monitor fix and all three monitor checks
pass after it. Collection resumes without restarting either physical job.

This is one controlled foreground USB experiment with the peer held. It does
not qualify server restart, client process death, prolonged network partition,
natural wireless Doze, long suspension, graph-boundary Stop, thermal endurance,
physical Release training or deployed HTTPS/TLS. Heartbeat round/step fields
remain fixed at registration. Provider counters include successful reported
rounds and omit failed-attempt traffic/compute; boundary temperatures are not
peak measurements. The private datasets and physical harness are hash-bound;
independent physical repetition is not claimed. Broad application regressions
were not repeated because product source is unchanged.
