# UI and Components

> **Current design system: Ledger** — navy structural ink (`#1C314D`) on quiet paper
> surfaces (`#F6F3EE` canvas, white cards), one type family (Hanken Grotesk; JetBrains
> Mono for logs/ids), 4px-grid spacing, quiet card shadows, and a light-first theme.
> Ledger landed in `2c50672` (2026-07-17) and superseded **Ember**, which had superseded
> **Instrument**. Tokens are generated — see below — and the dark palette (a navy-dark
> family, not pure black) stays wired for a future deliberate dark mode.

## Design tokens are generated, not hand-written

`design/tokens.json` is the single source of truth — its own `$description` field says so.
`node design/build-tokens.mjs` (dependency-free, plain Node) regenerates every per-platform
artifact:

| Artifact | Consumer |
|---|---|
| `frontend/src/styles/tokens.css` | Tailwind v4 `@theme inline` (semantic utilities: `bg-canvas`, `text-fg`, `border-hairline`, `bg-accent`, `shadow-card`, `text-h3`, …) |
| `fedlearn-desktop/src/renderer/tokens.css` | plain CSS custom properties incl. a `--text-*-size` / `-line` / `-tracking` / `-weight` ramp |
| `mobile_client/src/theme/tokens.generated.ts` | typed token object (`px` values stripped to numbers, durations to ms) |
| `mobile_client/src/theme/global.css` | NativeWind semantic color variables (`:root` light, `.dark` dark) |

Every generated file carries the header
`GENERATED by design/build-tokens.mjs — DO NOT EDIT. Edit design/tokens.json and re-run.`

**This is CI-enforced.** `.github/workflows/ci.yml` has a `design-tokens` job that runs
`scripts/check_design_tokens.sh` on **every** push — deliberately *not* path-filtered, unlike the
per-unit jobs. The script regenerates from `tokens.json` and fails if any committed output has
drifted, printing the literal fix (`node design/build-tokens.mjs`). It is the design-system
analogue of `check_proto_mirror.sh`.

Never hardcode a color, radius, shadow, or font in a component — consume the semantic tokens.
Palette changes are made once in `tokens.json` and propagate to all surfaces.

`--series-1…8` is a fixed-order categorical ramp (`#3565B0`, `#008300`, `#E87BA4`, `#EDA100`,
`#1BAF7A`, `#EB6834`, `#4A3AA7`, `#E34948`), identical in both themes and validated for

`16`→64px); shadows `card`, `card-hover`, `overlay`; durations `fast 120ms / base 180ms / slow 280ms`
with `ease-out` and `ease-in-out` curves.

### Type

One family for sans *and* display: `'Hanken Grotesk'` with a system fallback stack; `'JetBrains Mono'`
for logs, ids and numerics; `font-feature-settings: 'calt' 1, 'tnum' 1` (tabular numerals, so a
streaming metric does not jitter). Fonts are loaded by a `<link>` tag in `frontend/index.html`
(Google Fonts) rather than being self-hosted — `src/styles/fonts.css` exists only to record that,
and is otherwise empty. That is the one external asset host the SPA depends on.

The ramp is eight steps, each carrying size, line-height, tracking **and** weight:

| Token | Size / line | Tracking | Weight |
|---|---|---|---|
| `caption` | 12 / 16 | +0.1 | 500 |
| `label` | 13 / 18 | 0 | 500 |
| `body` | 14 / 20 | 0 | 400 |
| `body-lg` | 16 / 24 | −0.05 | 400 |
| `h4` | 18 / 24 | −0.2 | 600 |
| `h3` | 22 / 28 | −0.4 | 600 |
| `h2` | 30 / 36 | −0.6 | 600 |
| `h1` | 40 / 44 | −1 | 700 |

### Stylesheet layering

`src/styles/tailwind.css` is the entry point and the import order is load-bearing:

```css
@import "tailwindcss";
@import "./theme.css";   /* base layer + legacy shadcn aliases */
@import "./tokens.css";  /* GENERATED — semantic tokens win */
@import "./brand.css";   /* small expressive layer (eyebrow, legacy class shims) */
@import "./fonts.css";
```

`theme.css` does three jobs: it wires the `dark` variant for Tailwind v4
(`@custom-variant dark (&:is(.dark *))`), it **aliases the legacy shadcn-style names** to the
semantic tokens (`--card → var(--surface-1)`, `--muted-foreground → var(--fg-muted)`,
`--border → var(--hairline)`, …) so stray `bg-card` / `text-muted-foreground` / `border-border`
utilities in older components still resolve, and it sets the base layer (paper body background,
heading weight/tracking, selection colour, a slim themed scrollbar).

Those aliases are a **compatibility shim, not a second vocabulary** — new UI should use the semantic
tokens directly.

> **Dark mode is wired but not reachable from the web app.** `tokens.css` emits a full `.dark`
> block and `theme.css` defines the variant, but nothing in `frontend/src/` ever adds the `dark`
> class to the document, and there is no theme toggle in `SettingsView`. The web client is
> effectively light-only today; the dark family exists so a deliberate dark mode is a UI change
> rather than a palette project.

**Gotcha — custom class merging:** `src/lib/utils.ts` extends `tailwind-merge` with the token
scales so custom text *sizes* (`text-body`) and text *colors* (`text-accent-fg`) merge
independently. Without that config, stock tailwind-merge treats them as one group and silently
drops one. The `COLORS`, `TEXT_SIZES`, radius and shadow lists in that file are a hand-maintained
mirror of the token names — keep them in sync when adding a token.

## Component conventions (the rules the UI follows)

- **One primary action per view** — the navy fill. Secondary = white surface +
  hairline border; ghost = borderless; danger = solid destructive fill (a destructive
  confirm must never read weaker than Cancel; low-emphasis destructive entry points use
  ghost + a danger text class instead of the `danger` variant).
- **Dialogs** — everything goes through `ui/Modal`: portalled to `document.body`, scrim
  backdrop, overlay shadow, closes on backdrop click **and** Escape, focus trapped by
  `useFocusTrap` and returned to the trigger, footer slot with right-aligned natural-width
  `[Cancel] [Primary]`, sizes `sm`/`md`/`lg`. `ConfirmDialog` wraps it for confirmations, with a
  `danger` prop that switches the confirm button to the destructive variant.
- **Forms** — every control sits in `ui/FormField`, which generates an id with `useId()` and
  `cloneElement`s it onto its **single** control child so the `<label htmlFor>` pair is always
  programmatically linked. Passing two children breaks that association — put anything extra
  beside the `FormField`, not inside it. Specific verb labels ("Create project", not "Submit");
  loading state renders inside the submit button; an `error` slot replaces `help` while present.
- **Page shell** — every routed view renders `PageHeader` (a sticky `h-16` bar: `text-h3` title,
  truncated `text-label` subtitle, right-aligned action slot) over a
  `mx-auto max-w-[1400px] px-6 py-6 md:px-10` content container. Live-connection state is a quiet
  dot+caption chip in the header actions, never part of the title.
- **Status** — `ui/StatusPill` is the only status vocabulary (no emoji, no unicode glyphs, never
  repurposed for non-status data). Its five kinds map to tokens as
  `running → accent · completed → success · error → danger · pending → warning · idle → fg-muted`,
  and the exported `toStatusKind()` is the one domain mapper
  (`INITIALIZING → pending`, `RUNNING → running`, `COMPLETED → completed`, `FAILED → error`,
  everything else → `idle`).
- **Stats** — `ui/StatGroup` (one card, hairline-divided) instead of card-per-number grids.
- **Micro-labels** — `ui/SectionLabel` is the one uppercase label style.
- **Empty states** — neutral lucide icon in a muted circle + title + one-line body.
  The brand mark is a logo, not illustration.
- **Icons** — `lucide-react` only.
- **Charts** — Recharts, with series colors from the `--color-series-N` tokens in fixed assignment
  order; one axis per chart (no dual-axis), legend for ≥2 series.
- **Focus** — every interactive element has a visible `focus-visible` ring (2px accent, offset 2).

## The project-creation picker and the training arm

Creating a project and starting a run are **two different decisions in two different modals**, and
the training arm belongs to the first:

| Modal | Opened from | Decides |
|---|---|---|
| `CreateProjectModalV2` (`redesign/CreateProjectModal.tsx`) | `OwnerDashboard` → *New project* | name, model recipe, base model, optimizer, warm-up rounds, LoRA task type, and — where offered — the **training arm** |
| `StartProjectModal` (`redesign/StartProjectModal.tsx`) | a project card's *Start* action | aggregation strategy, number of rounds, minimum clients |

The arm is a **project** property, not a per-run one: it is persisted on
`projects.training_arm VARCHAR(32) NOT NULL DEFAULT 'FULL'` (Flyway `V22__project_training_arm.sql`,
its CHECK widened to include `OVA_LP` by `V23__training_arm_ova_lp.sql`), so it is chosen once at
creation and every run of that project inherits it.

`StartProjectModal` offers six training methods — FedAvg, FedProx, DeComFL, FedOpt, Robust and
FoT — each with a plain-language label, except for an `LLM_LORA` project, where the method is not a
choice at all: the modal renders a read-only "FedLoRA (automatic for LoRA fine-tuning)" field.

### How the picker works

1. On open, the modal fetches `GET /api/model-recipes` (`fetchModelRecipes`). If that fails it falls
   back to a two-entry local list (`CNN`, `TRANSFORMER`) purely so the modal stays usable offline —
   the catalog is always the primary source.
2. Changing the model type resets base model, optimizer, task type, and the arm back to `FULL`.
   Recipes differ in which arms they declare, so carrying a stale selection across a model change
   could submit an arm the new recipe never offered.
3. The arm control renders **only when the recipe declares more than one arm**:
   `offersArmChoice = (selectedRecipe?.supportedArms?.length ?? 0) > 1`. A single-arm recipe shows
   no control *and no trade-off* — rendering one would imply the un-offered arm had been evaluated
   for that recipe.
4. `trainingArm` is included in the create payload **only** when `offersArmChoice` is true, so the
   request never asserts an arm the recipe did not declare. The default is `FULL`, which reproduces
   the behaviour that existed before arms were a concept.

### Where the numbers come from

The trade-off panel beside the control is a *rendering of a measurement*, and the chain is
deliberate at every hop:

```
research/results/…/<run>.json          the raw measured record
   └─ scripts/build_arm_tradeoff.py    generator (records source path + source_sha256 + date)
        └─ fl-runtime/arm_tradeoff.json     keyed BY RECIPE under "by_recipe"
             └─ recipes.py describe()       attaches arm_tradeoff only when len(supported_arms) > 1
                  └─ GET /api/model-recipes (ModelRecipeDto.ArmTradeoff)
                       └─ CreateProjectModal  headline · per-arm summary · measuredOn · caveats
```

`arm_tradeoff.json` currently carries entries for `PNEUMONIA_CNN`, `CNN` and `CIFAR_RESNET18`. The
lookup is strictly keyed — an earlier version attached one chest-X-ray result to *every* dual-arm
recipe, which made a CIFAR-10 recipe advertise a pneumonia figure. A missing entry returns nothing
rather than raising, so an absent measurement costs the user an explanation, not the ability to
create a project.

The component states no figure of its own. It renders, in order: the record's `headline`, the
selected arm's `summary`, a "Not feasible on-device" line **only** when `ondeviceFeasible === false`
(a measured `null` means *not measured* and must render as absence, not as a claim either way), the
`measuredOn` task and protocol, and the `caveats` list inside a collapsed
*"What this measurement does not establish"* disclosure. The caveats are not garnish — the
communication ratio is round-budget dependent and the accuracy and latency figures can come from
different hardware, so a number shown without them would state more than was measured.
`CreateProjectModalArm.test.tsx` pins each of those properties, including that the choice still
renders when the catalog carries no trade-off at all.

One backend detail that protects this display: `ModelRecipeDto.ArmTradeoff.commRatio` is a `Double`,
not an `Integer`. Every measured ratio was a large whole number until `PNEUMONIA_CNN` came in at
**1.004×** (its classifier is 99.6% of the model, so freezing saves almost nothing) — and Jackson
coerces a JSON float into an `Integer` by *truncating*, which would have rounded an honest 1.004
down to 1 on its way to the picker.

### Known gap — the third arm is not in the UI yet

`fl-runtime/recipes.py` and the backend `TrainingArm` enum both define **three** arms —
`FULL`, `FROZEN_HEAD` and `OVA_LP` (one-vs-all linear probing on a frozen encoder, which differs
from `FROZEN_HEAD` in its *objective* rather than its parameter subset) — and `CIFAR_RESNET18`
declares all three. The frontend has not caught up:

- The `<option>` list is built from `supportedArms`, so `CIFAR_RESNET18` **does** render three
  options — but the label is a binary ternary
  (`a === 'FROZEN_HEAD' ? 'Frozen backbone — train the head only' : 'Full fine-tune'`), so `FULL`
  and `OVA_LP` both read as "Full fine-tune". Two identically-labelled options is the visible
  symptom.
- `arm_tradeoff.json`'s `CIFAR_RESNET18` entry has only `FULL` and `FROZEN_HEAD` arms, so selecting
  `OVA_LP` shows the headline and caveats with no per-arm summary.
- `Project.trainingArm` in `apiServices.ts` is typed `'FULL' | 'FROZEN_HEAD'`, so a project created
  on `OVA_LP` is mistyped on read.

The label map, the trade-off generator and that union type are the three places to update when
`OVA_LP` is surfaced. Nothing here is a data-loss bug — the value round-trips correctly through
the API, the DB CHECK and the FL runtime; it is the *presentation* that has not caught up.

## App structure

Views live in `src/components/redesign/` (the `redesign/` path is historical — it is
the only UI; the old `/v2` routes redirect to the canonical paths). `LayoutV2`
composes `Sidebar` + routed view; auth pages live in `src/pages/`. `ErrorBoundary`
wraps the app; `DiskLoader` is the standard async spinner. Brand assets
(`favicon.svg`, `favicon.png`, `apple-touch-icon.png`, `icon-192/512.png`, `og-image.png` in
`frontend/public/`) carry the flat navy network mark and are regenerated alongside palette changes;
`index.html` pins `<meta name="theme-color" content="#F6F3EE">` to the Ledger canvas.

## Responsive design

Layouts reflow with Tailwind breakpoint prefixes (`md:flex`, `lg:grid-cols-3`);
tables scroll horizontally inside their cards on narrow viewports.
